# Pedagogy review: Attempt History Snapshot

## Decision
APPROVE WITH CHANGES

The proposal targets the same RO/AC gap (charter §2.5) that the hypothesis-card decision addresses, but on the *backward-looking* side — making prior cycles externally inspectable so they don't have to be held in working memory under PF cognitive load. The category is appropriate; the trigger, granularity, representation, and condition equivalence must be tightened so the panel does not collapse into a score-like signal or a similarity-to-solution leak.

## Why this decision
- §2.5 names "attempt history snapshots" as theoretical infrastructure for converting CE into RO, on equal footing with hypothesis cards. Approving the category is consistent with the charter.
- §2.5 constraint: RO/AC affordances must not collapse into hint-giving in PF. A history view is *backward-looking only* — it shows what happened, never evaluates it — so it sits inside the allowed boundary if (and only if) it is built without quality cues.
- §6 forbids score-like signals, comparison framings, and "you've been here a while" time-pressure prompts. Several otherwise-natural design moves (count of attempts, "closest so far" highlight, time-since markers) would violate this and must be excluded.
- §2.6 GBL principle "world-as-feedback, not system-as-judge" applies: the panel must depict topology, not adjudicate it.

## Acceptance criteria
1. **Identical behavior across PF and DI.** Same trigger, same K, same representation, same placement (§2.5 — RO is metacognitive, not condition-specific).
2. **Trigger: stable-state on iteration boundary, not time-based and not topology-event-based.** Capture a snapshot when *both* hold: (a) a `socket_disconnect` or `socket_connect` has occurred and (b) the next `socket_connect`, `socket_disconnect`, `grab_start`, or `task_complete` has not occurred for ≥ 1500ms. The dwell exists only as internal de-bouncing — it is never surfaced in the UI, never spoken about, never used to prompt the learner. This satisfies §6 because the time threshold is invisible to the participant; it is a sampling rate, not a time-pressure prompt. Recording sampling rates is already standard in the existing telemetry pipeline (e.g., gaze dwell windows).
3. **Representation: 2D abstract socket-grid icon, no LED state, no quality cue.** Each thumbnail shows occupied sockets as neutral grey marks on the board outline, with component type optionally encoded by *shape* (square = battery, line = wire, circle = LED, triangle = resistor) — never by color saturation, never with the LED rendered as lit/unlit, never with a checkmark or X. Forbidden: green/red coloring, "closest so far," highlight of the most-recent change, similarity-to-target overlay.
4. **K = 4 thumbnails, FIFO, no count label.** No "Attempt 3 of N," no enumeration, no timestamp, no duration. Most-recent on one end, oldest dropped. The panel's existence implies recency; no number is needed.
5. **Read-only.** No click-to-replay, no click-to-restore, no hover tooltip with details, no "go back" affordance. Touching a thumbnail does nothing. (Replay/undo is forbidden by §6 logic — it short-circuits generative struggle.)
6. **Placement: peripheral and ignorable.** Hand off positioning to `ux-feel-critic` with constraint "outside the breadboard's working sightline; visible without head-turn but not in central FOV." Must not animate in/out; thumbnails appear without transition.
7. **De-duplication.** If a new snapshot is byte-identical (same set of `{id, a, b}` placements) to the most recent stored snapshot, do not store it. Prevents jitter from accidental near-instant re-snaps inflating the panel.
8. **Telemetry contract.** Emit `attempt_snapshot { snapshot_index, placements: [{id, a, b}], trigger_reason: "stable_dwell" | "task_complete" }`. Existing `circuit_topology` semantics unchanged; the new event is a *coarser* derived stream, not a replacement. Do not emit per-thumbnail render events.
9. **Removal criterion.** Remove if pilot data show any of: (a) panel-glance gaze dwell exceeds breadboard gaze dwell within a cycle (indicates the panel has become the task), (b) participants verbalize attempt counts as a score ("attempt 3 again, ugh"), (c) post-test variance on near-miss precision drops in both conditions equally (indicates the panel homogenized manipulation strategy by enabling pattern-matching). Pre-register in analysis plan.

## Required changes
- **Trigger** — drop Options A, C, D from the proposal. Option A (`task_complete` only) is too sparse for PF where most cycles fail. Option C (LED state change) ties the snapshot to the *outcome* dimension, which is the score-leak vector — a learner would learn "snapshots = success moments." Option D (every connect/disconnect) produces the visual clutter the proposal anticipates. Use the iteration-boundary stable-dwell trigger above.
- **Time-based concern (§6)** — explicitly addressed: the 1500ms dwell is a *sampling de-bounce* internal to the system, not a participant-visible time pressure prompt. §6 forbids prompts like "you've been here a while"; it does not forbid sampling intervals. Charter compliance hinges on the dwell *never* being surfaced in UI text, audio, or affordance state. Document this distinction in the implementation as a comment so future contributors don't accidentally surface it.
- **Representation** — drop Option A (3D rendered breadboards: GPU cost on a research target, plus the physical realism makes it feel like "rewind the world," which invites replay expectations). Drop Option C (text: strips embodied/spatial encoding entirely — defeats §2.2). Use Option B with the constraints above.
- **K** — proposer offered 3 or 5; pick 4. Three loses the iteration-cycle context (you can only see 1 prior + current attempt logic); five starts to feel like a scoreboard. Four shows enough variation to be useful for self-comparison without enumerating "how many tries."
- **Interaction** — read-only, as proposer recommended. Confirmed.
- **Snapshot when task completes** — store the final successful topology as the K-th slot with no special styling (no glow, no checkmark, no "solved" badge). The fact that the LED on the live board is lit is the only success signal; the history panel stays neutral.

## Threats to validity
- **Pattern-matching collapse of generative struggle.** The strongest threat. If learners see four prior topologies side-by-side, they may treat the task as visual-pattern combinatorics rather than causal reasoning about charge flow. Mitigation: abstract icon-grid (not photorealistic), no LED state shown, removal criterion (c) above. This threat is real and should be explicitly tested in pilot — code reflection text for whether learners describe the panel in pattern-matching terms ("I tried this layout, then this one") versus causal terms ("the loop wasn't closed last time").
- **Score-creep via implicit count.** Even without a number, four visible thumbnails communicate "you've tried four things." This *is* a count, just non-numeric. Acceptable because four is bounded and FIFO erases history beyond it; a learner cannot infer "I'm on attempt 11" from the panel alone. If pilot reflection coding shows count-as-score language, raise to research lead.
- **Embodied encoding dilution.** §2.2 hypothesizes that 6DoF manipulation alters *encoding* of failure. A symbolic 2D representation of past failures is a different encoding channel — it could either reinforce (by externalizing what was felt) or compete with (by substituting a symbolic snapshot for the felt state) embodied memory. This is unresolved theoretically and must be flagged in the analysis plan as a known limit.
- **Condition × panel interaction with hypothesis-card.** Once both this and the hypothesis card ship, PF and DI both receive two metacognitive scaffolds. If main-effect on post-test is positive, the design cannot separate "embodied PF" from "PF + RO scaffolds." This is a known limit of the planned 2026 study; flag in pre-registration. Single-feature pilots before joint deployment recommended.
- **Demand characteristic.** A panel showing prior states implies "you should compare and revise." That's the intended affordance — but in PF, it could leak the meta-instruction that earlier attempts were wrong. Net leak is small (LED state already conveys this) but log it.

## Open questions for the human
1. **Pilot order.** Recommend piloting hypothesis card and attempt history *separately* before joint deployment, so each one's contribution is identifiable. Confirm sequencing.
2. **Component-shape encoding.** Does encoding component type by shape (square/circle/line/triangle) leak structural information that the bare goal description does not? My read: no, because the player already sees component types in 3D on the workbench and tray. Confirm.
3. **Transfer task (§2.4) parity.** When modular synth lands, the panel must use a representation that is neutral across both task surfaces — likely a node-and-edge graph rather than a board grid. Defer detailed spec until that task arrives, but note now so the implementer does not hardcode breadboard geometry.
4. **Storage scope.** Snapshots are session-local (in-memory, K=4 FIFO). Do we also persist them to telemetry for post-hoc replay analysis? Recommend yes via the `attempt_snapshot` event, no via local storage. Confirm.
